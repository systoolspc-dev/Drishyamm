# Dense-crowd "people" detector (YOLO26-M), recall-limited

## 1. What it detects

| id | class |
|---|---|
| 0 | people |

- The labels are small boxes in dense crowds (head-sized: median **12x16 px** at 640).
- Source: Roboflow Universe `vidit-ghai/crowd-counting-dataset-w3o7w-bdoyn` v1, exported 2026-05-19.

## 2. Architecture and training recipe

| item | value |
|---|---|
| architecture | YOLO26-M (end2end NMS-free), 21.77 M params, 75.0 GFLOPs at 640 (unfused) |
| base | `yolo26m.pt` COCO-pretrained |
| imgsz / batch / epochs | 640 / 16 / **100, completed** (patience 100) |
| optimizer | auto (lr0 0.01, lrf 0.01, mom 0.937, wd 5e-4) |
| augmentation | mosaic 1.0 (close 10), hsv 0.015/0.7/0.4, translate 0.1, scale 0.5, fliplr 0.5 |
| **max_det** | **300** (default; applies at validation and is the size of the YOLO26 one-to-one output) |
| other | `workers: 2`. `train_yolo26.py --gpu-fraction` caps VRAM via `torch.cuda.set_per_process_memory_fraction` (the log shows 30 %) |
| wall time | 8,105 s (about 2.3 h) |
| Ultralytics | 8.4.52 (log shows 8.4.46 for an early attempt), 2026-05-21 |

Run history:
- `train`, `train-2` … `train-10` and `train-13` (mostly batch 64) have no weights. They were failed or
  aborted attempts, probably OOM under the VRAM cap.
- `train-11` (6 epochs) and `train-12` (3 epochs) are partial runs.
- **`train-14` is the final run.**

## 3. Results (valid split, 435 images)

| row | epoch | P | R | mAP50 | mAP50-95 |
|---|---|---|---|---|---|
| final = best fitness (shipped) | 100 | 0.789 | **0.468** | 0.490 | 0.245 |
| best mAP50 | 99 | 0.788 | 0.468 | 0.491 | 0.245 |

- Loss trend, epochs 1 to 100: train box 2.94 to 1.95, cls 1.95 to 0.90. Val box 2.89 to 2.20, val cls 1.88
  to 1.06. Still decreasing slowly.
- Plots included in `project/runs/detect/train-14/`: confusion matrices, PR/P/R/F1 curves, `results.png`.

**Why recall is stuck near 0.47.** Precision is reasonable (0.79): what it finds is usually a person.
Recall is capped by three structural limits:
1. **`max_det = 300`.** About a fifth of the validation images contain more than 300 people. The YOLO26
   end-to-end head emits at most `max_det` candidates, so anything past 300 can never be counted.
2. **Object size.** The median box is about 12x16 px and the 10th percentile is about 3 px wide at 640.
   That is at or below the P3 stride-8 cell, so many heads are physically unresolvable at 640.
3. **Ambiguity.** In very dense crowds, partially visible heads with inconsistent labels hurt both mAP and
   the loss.

## 4. Inference

```python
from ultralytics import YOLO
m = YOLO("project/runs/detect/train-14/weights/best.pt")
r = m.predict(frame, imgsz=1280, conf=0.25, max_det=2000)[0]   # raise max_det for crowds
count = len(r.boxes)
```
- **Preprocessing:** letterbox to `imgsz`, RGB, divide by 255.
  - Note the train/serve mismatch: training images were **stretched to 640x640**, while live 16:9 frames are
    letterboxed with the aspect ratio preserved.
  - So people look relatively "wider" in training than at inference. Consider stretching live frames to a
    square too, or retrain on unstretched data.
- **Postprocessing:** end-to-end top-k of `max_det` rows `[x1, y1, x2, y2, score, cls]`. No NMS. An export
  has a fixed `max_det` baked in, so set it at export:
  `yolo export model=best.pt format=onnx imgsz=1280 max_det=2000` (verify that your Ultralytics version
  honours `max_det` for end2end export).
- **Platform status: NOT integrated.**
  - The deployed head-count service (`smart-cam-ai/app/head-count`) uses a different 6.2 MB model,
    `models/abel/best.pt`.
  - `zone-sim` uses `yolov8n.pt`.
  - Crowd-surge alerts (`crowd.stampede`) come from the separate stampede project via a backend webhook
    (`smart-cam-backend/src/routes/internal.routes.js`). See `../stampede-anomaly`.

## 5. Known weaknesses

- **Recall about 0.47.** Detection undercounts dense crowds by roughly half, and the cap is structural
  (see above).
- **Probable split leakage, filename evidence only.** 265 of 402 unique valid source stems and 304 of 357
  test stems also appear in train. The generic names (`img_529_jpg`) could be collisions from merged
  datasets, so this is unverified.
- Stretch-resized squares: there is a geometry mismatch with real CCTV.
- No negatives (no empty frames) and no sparse scenes. Behaviour on 0 to 20 people per frame is unknown.
- Head-sized targets at 640 are the hard regime for any single-scale detector.

## 6. Improvement ideas (embedded)

1. **For counting dense crowds, use density estimation, not boxes.** The CSRNet path in
   `../stampede-anomaly/stempade_gpu_csrnet` regresses a density map and has no `max_det` ceiling. Use this
   detector only where people are countable (fewer than about 150 per view).
2. **If staying with detection:**
   - Retrain with `max_det=1500` (train-time validation then counts correctly) and imgsz 1024 to 1280.
   - Or tile frames into 640 crops with overlap (SAHI-style) and merge boxes across tiles.
   - Re-export the dataset **without** stretch resize.
3. **Small-object tuning.** Increase `scale` augmentation range and keep `mosaic`. Consider a P2 head
   variant (`yolo26m-p2` style yaml, if available) for stride-4 features.
4. **Edge budget.** YOLO26-M at 1280 is about 300 GFLOPs per frame. For edge, distil to `yolo26s` at 960:
   `YOLO("yolo26s.pt").train(data="data_portable.yaml", imgsz=960, max_det=1500, distill_model="<this best.pt>")`.
   Then `yolo export … format=engine half=True` (or `int8=True data=data_portable.yaml`).
5. **Temporal smoothing for counts.**
   - Report a rolling median over 2 to 5 s, not per-frame counts.
   - Alert on occupancy thresholds only after the smoothed count stays above the threshold for N seconds.
   - See `../../docs/DETECTION_DECISION_ALERT_FRAMEWORK.md` and `../../docs/OCCUPANCY_LOGIC.md`.
6. Build a test set with ground-truth counts from your own cameras. Report MAE and MAPE of counts as well
   as mAP.
